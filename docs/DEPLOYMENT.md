# Deployment guide (Neon + Render + Cloudflare Pages)

Everything below uses free plans. Do the steps in order; each one produces a value the next one needs. Never paste real secrets into chat, issues or git: they go only into the provider dashboards or your own shell.

Architecture:

```
Browser ──> Cloudflare Pages (static site)
              └─ /api/*  ──(Pages Function proxy)──> Render (Express API) ──> Neon (PostgreSQL)
                                                          └──> Cloudinary (images)
```

## 0. Before you start
- The code is on GitHub (`main`). Render and Cloudflare deploy from it.
- You need accounts at Neon, Render and Cloudflare (sign in with GitHub is fine). Your Cloudinary credentials already exist in your local `.env`.
- Read `FREE_HOSTING_COMPARISON.md` once: the first visit after idle is slow by design.

## 1. Neon (database)
1. Create a project: region **AWS Asia Pacific (Singapore)**, PostgreSQL 16 or newer, database name `shopsphere`.
2. In **Connect**, copy two connection strings:
   - **Pooled** (host contains `-pooler`): this becomes `DATABASE_URL` on Render.
   - **Direct** (toggle "pooled connection" off): this becomes `DIRECT_URL` (used for migrations and for seeding).
3. Keep both strings private. They contain the password.

## 2. Create the schema and the data (from your computer)
Run in PowerShell from the repository root. Replace the angle-bracket values; choose your own admin password (at least 8 characters, no `#`):

```powershell
$env:DATABASE_URL = "<Neon DIRECT connection string>"
$env:DIRECT_URL   = $env:DATABASE_URL
$env:JWT_ACCESS_SECRET  = "x" * 40      # placeholders: the seed scripts load the config but never sign tokens
$env:JWT_REFRESH_SECRET = "y" * 40
$env:SEED_ADMIN_EMAIL    = "admin@shopsphere.demo"
$env:SEED_ADMIN_PASSWORD = "<choose a strong password>"

pnpm --filter @shopsphere/api prisma:generate
pnpm --filter @shopsphere/api migrate:prod          # creates all tables and rules
pnpm --filter @shopsphere/api seed:prod             # admin, categories, brands
pnpm --filter @shopsphere/api demo:seed:prod        # optional: demo sellers, buyers, 39 products, reviews, coupons
```

Close the PowerShell window afterwards so the variables disappear. Skip `demo:seed:prod` if you want an empty store.

## 3. Render (API)
1. Dashboard > **New > Blueprint**, choose the `shopsphere` repository. Render reads `render.yaml`.
2. Fill the prompted values:
   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | Neon **pooled** string |
   | `DIRECT_URL` | Neon **direct** string |
   | `CORS_ORIGIN` | your site's exact origin, e.g. `https://shopsphere.pages.dev` (you can edit it after step 4; no trailing slash) |
   | `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` | from your Cloudinary dashboard |
   `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are generated by Render automatically.
3. Deploy. The build installs, bundles the API and runs pending migrations. Wait for **Live**.
4. Check `https://<your-service>.onrender.com/api/v1/health`: it should return `{"success":true,"data":{"status":"ok","db":"up",...}}`. The first call may take about a minute.
5. Note the service URL (`https://<name>.onrender.com`).

`DEMO_MODE` is set to `true` in `render.yaml` on purpose (a public demo has no email delivery, so password-reset tokens are shown on screen). Change it to `false` if this ever holds real accounts.

## 4. Cloudflare Pages (website)
1. **Workers & Pages > Create > Pages > Connect to Git**, choose the repository.
2. Build settings:
   - **Root directory:** `apps/web`
   - **Build command:** `npm install -g pnpm@12.23.0 && pnpm install --frozen-lockfile && pnpm build`
   - **Build output directory:** `dist`
   - Environment variable `NODE_VERSION` = `22`
3. Add the runtime variable for the proxy (Settings > Variables and Secrets, **Production**): `API_ORIGIN` = `https://<name>.onrender.com` (no path, no trailing slash). Do **not** set `VITE_API_URL`; the site calls its own `/api`.
4. Deploy, then open the site address (`https://<project>.pages.dev`).
5. Go back to Render and make sure `CORS_ORIGIN` equals that exact address; redeploy if you changed it.

## 5. Verify the live site (tell me when it is up and I will run the live checks)
- `https://<site>/api/v1/health` returns ok through the proxy.
- Home page shows the demo products; images load.
- Register a buyer, sign in, **reload the page: you stay signed in** (this proves the cookie works).
- Place a COD order; sign in as `seller.technest@shopsphere.demo` (`ShopDemo2026`) and accept/ship it; sign in as admin and open Reports, Settlements and Settings.
- Open the site after 20 minutes of silence: you should see the "demo server is waking up" notice and then the page.

## Updating
Push to `main`: Render and Cloudflare redeploy automatically; migrations run on the Render build. Never edit an applied migration; add a new one.

## Rollback
Render: service > Events > Rollback to a previous deploy (the last two are kept). Cloudflare: Deployments > Rollback. Database changes are not rolled back automatically, so make migrations additive.

## Troubleshooting
| Symptom | Likely cause |
|---|---|
| Signed out on reload | `CORS_ORIGIN` does not match the site origin exactly, or `COOKIE_SAMESITE` was changed from `lax` |
| `PROXY_NOT_CONFIGURED` from `/api/...` | `API_ORIGIN` missing or invalid on Cloudflare (set it for **Production**, then redeploy) |
| `API_UNAVAILABLE` after about a minute | Render instance failed to start: read its logs (usually a wrong `DATABASE_URL`) |
| Slow first request after idle | Expected: Render wakes in about a minute, Neon resumes in seconds |
| Build fails at migrate | `DIRECT_URL` missing on Render, or the database is unreachable |
| Images missing | Cloudinary variables missing; demo images are already hosted there |

## Status of the Neon database (updated)
The Neon project (`shopsphere`, Singapore, PostgreSQL 18, branch `production`) already has the schema, the admin account and the demo data applied (verified: 3 migrations, 27 categories, 20 brands, 39 products, 135 reviews, 5 buyers, 3 sellers). Step 2 of this guide is therefore done; start at step 3 (Render). The admin password for that database is stored only in your local, git-ignored `.env.neon`.

Notes from the Neon verification:
- Connection strings contain `sslmode=require`. The `pg` driver prints a harmless warning about it; use `sslmode=verify-full` in the Render variables to keep the same behaviour without the warning.
- Do not run `neon deploy` or `neon env pull` without `--file .env.neon`: by default they write into `.env` and replace your local `DATABASE_URL`.
